# Everline Design Agent 操作事故報告

日期：2026-08-14
專案：Everline Design
影響範圍：PR #49～#54、相關 worktree、部分專案歷史紀錄
狀態：Recovery in progress

## 1. 摘要

2026-08-14 凌晨，Everline Design 在處理 PR #49～#54 的
Human G1 review 後續工作時發生 Agent scope-control 事故。

事故起點為一份將多支彼此獨立 PR 整合成單一長程目標的
Agent 提示詞。

該提示詞沒有充分尊重：

- 每支 PR 使用獨立 branch / worktree
- 每支 PR 有獨立 Human review 狀態
- shared catalog files 雖然重疊，但不代表 PR 應被視為單一批次修改

後續 Agent 因此在多支 PR 中執行修改。

之後進行日期修正時，又因歷史事實來源處理錯誤，
將當前日期 2026-08-14 誤作 Human G1 review 日期，
並進一步產生跨 PR 修復與錯誤事實紀錄。

多次後續修復反而提高狀態理解成本，
造成使用者必須花費大量時間與模型 token
進行 Git 狀態確認與事故分析。

## 2. 事故觸發原因

主要觸發原因：

1. 將 PR #49～#54 打包為一個長程 Agent goal。
2. 沒有限制 Agent 必須一次只操作單一 PR / worktree。
3. shared files 被錯誤解讀為可以跨 PR 統一處理。
4. 歷史 Human review 日期沒有強制從 GitHub 原始紀錄取得。
5. 第一次錯誤發生後，修復策略仍然過大，沒有立即停止寫入並縮小 scope。

部分文件將 Human review 日期記錄為：

後續曾嘗試訂正這些日期，
但因 recovery scope 再次擴張，
導致多個 worktree 同時出現未提交日期修正。

## 7. Recovery 決策

原本曾考慮逐項保留：

- #49 regression test
- #51 Tabs hover redesign
- #54 Toast alignment fix
- #50/#52/#53 正確 graduation state

但這種方式需要逐 commit、逐檔案、逐歷史事實重新判斷，
Recovery 成本已高於使用者願意繼續投入的時間與 token。

最終決策：

完整撤銷 2026-08-14 05:05～05:34
PR #49～#54 的六個 incident commits。

採用 git revert，
不採用 reset / rebase / force-push。

目標是讓每支 PR 的實際 tree
回到 incident commit parent 的內容，
同時保留可追溯 Git 歷史。

## 8. 根本原因

### Prompt scope 過大

最初 Agent prompt 將六支獨立 PR 視為一個整合工作項目。

這是本事故最主要的設計錯誤。

### Fact authority 不清楚

Human review 日期屬歷史事實，
應從 GitHub comment 原始 timestamp 查證。

Agent 不應使用目前日期進行推斷。

### Recovery 過度複雜

第一次錯誤後沒有立即停止修改，
而是持續產生新的修復提示詞。

造成：

錯誤修改
→ 日期修正
→ 跨 PR scope expansion
→ recovery worktree 修改
→ 更多狀態分析

Recovery 本身逐漸成為事故的一部分。

## 9. 後續規則

未來處理多 PR Agent 工作時：

1. 一個 PR = 一個操作 scope。
2. 一個 worktree = 一個獨立工作單位。
3. shared files 不代表 PR 可以合併處理。
4. Human decision / review date 必須引用原始證據。
5. Agent 不得從 system date 推測歷史事實。
6. 發生 scope-control 事故後立即停止寫入。
7. Recovery 第一階段只能盤點，不應直接修改。
8. 未經明確授權不得跨 PR 修復。
9. 不使用「順便整理」作為 recovery 的一部分。
10. 回滾優先選擇可追溯的 git revert，避免不必要的 history rewrite。

## 10. 最終影響

本事故主要影響：

- 開發時間
- Agent token 使用量
- PR 狀態可信度
- Human review 歷史紀錄可信度
- 使用者對自動化修復流程的信任

目前沒有證據顯示 main 的核心 Everline Design
功能內容因六支 PR 的凌晨修改而被直接覆寫。

Recovery 完成後，
PR #49～#54 將重新從事故前狀態繼續人工審查與開發。
